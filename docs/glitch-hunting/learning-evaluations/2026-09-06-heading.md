# Corrected-heading native check

Question: does correcting maintained-heading execution make the existing
learning loop useful, and what still limits it?

The campaign used orchestrator source `b2947c36b1`, built with the `campaign`
profile, and the existing August 4 native game build. It used no demonstration,
four sequential seeds with shared experience, two native workers, two proposals
per decision, and 32 decisions per seed. The episode horizon was 1,024 ticks.
These are not four independent training runs.

## Result

- Best authenticated terminal: 468 ticks. Two seeds produced terminal outcomes;
  another only inherited support. No route passed the promotion threshold.
- 128 decisions produced 256 proposal transitions. The reachability model was
  primary on 25 decisions. Policy-update probes attributed seven changed
  selections to updates, which does not establish better subsequent outcomes.
- Checkpoint use is real: 130 direct restores and 118 direct continuations,
  with no direct-restore fallback failures. However, there were also 564 root
  restore requests and 169,518 replayed prefix ticks, alongside 12,197 reported
  native ticks. Search and evidence work still repeat substantial prefixes.
- Total reported wall time was 235.8 seconds; model updates took 60.8 seconds.
  The optimized orchestrator build took 7 minutes 15 seconds beforehand.
- `--wall-micros` is currently checked against each seed's elapsed time, not
  the whole campaign. The requested 180-second value was therefore not a
  three-minute aggregate cap. Every seed stopped at its decision limit.

This check did not improve on the earlier 257-tick result. The family identity
and generated candidates changed, and the older campaign used a different
orchestrator build/profile; this is not an isolated causal comparison of route
quality or throughput. The heading regression establishes a semantics fix,
not an adequate learner. No additional native mining was launched here.

The next learning work should address the weak connection between experience,
delayed outcome value, and subsequent exploration choices, including checkpoint
reuse. Tuning the immediate-progress calibration score is not the success goal.
